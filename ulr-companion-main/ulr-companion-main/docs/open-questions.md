## 1. 角色 ID 用什麼？ 🔴 擋住 WP-02

規格書自己前後不一致：

| 出處            | 寫法                                                    |
| --------------- | ------------------------------------------------------- |
| 附錄 A 規則範例 | `"WOLAND_L4": 21.0`                                     |
| §8.3 戰果匯入   | `"team": ["CHAR_L4_001", "CHAR_L4_028", "CHAR_R1_009"]` |

而**遊戲封包實際給的是第三種**（來自既有 Python 研究程式的實測）：

```jsonc
// db_deck1 的牌組內容
{ "chara1": "cc078", "charaIndex1": 775, ... }

// 戰鬥中的 chara_A 事件
{ "chara": "cc078", "charaIndex": 775, "level": 4, "hp": 10, "atk": 8, "def": 1 }
```

也就是 `cc###`（角色）+ `charaIndex`（卡片實例）+ `level`（等級）。

**建議：規則的鍵用「角色代號 + 等級」，直接從封包的 `chara` + `level` 組出來。**

```
cc078_L4
```

理由：

- 插件不必維護一張「cc078 → WOLAND」的對照表，少一個會漂移的資料來源
- 遊戲改版新增角色時，規則作者不用等插件更新就能寫新規則
- `charaIndex` 是卡片實例編號（同一角色每張卡不同），**不能**進規則

代價：規則檔對人不好讀。可以在 ULGG 的規則頁做顯示層的對照，不進 Hash。

> 現況：`schema/cost-rule.schema.json` 的 `entityId` 暫時用寬鬆的
> `^[A-Za-z0-9_.-]{1,48}$`，三種寫法都收。**定案後要收緊。**

## 2. 壓 C 的「差距」是誰跟誰的差距？ 🔴 擋住 WP-02

燈皇的規則是「差距 7~13C → +5C，差距 6C → +1C」。但「差距」的定義沒寫清楚：

- (a) 我方隊伍總 COST 與對方隊伍總 COST 的差距？
- (b) 隊內最高 COST 角色與最低 COST 角色的差距？
- (c) 隊伍總 COST 與上限的差距？

(a) 的話插件必須先知道對方的牌組，那要嘛靠雙方回報、要嘛靠封包
—— 但**對手牌組是隱藏資訊，§12 明訂不得使用**。所以如果是 (a)，
就只能在雙方都回報給 ULGG 之後才算得出來，Cost Engine 不能是純函式，
整個設計會不一樣。

`GapBand` 的型別已經定好（`minGap`／`maxGap`／`extraCost`），
但**這題沒答案之前 `calculateTeamCost` 寫不出來**。

## 4. 「假 OK」拖條方案 🟡 技術上已驗證可行，但**不在 MVP 範圍**

社群最痛的議題。要解決的原始問題（燈皇原話）：

> 按下 OK 後就會鎖定，對方操作時也無法解除我的鎖定，這是這遊戲的不良設計。

也就是你先承諾、對手看到你已鎖定之後可以慢慢磨，你卻改不了。

### 已實測確認的事實（2026-07-28）

| 項目                               | 結果                                                               |
| ---------------------------------- | ------------------------------------------------------------------ |
| `WSClient.prototype.emit` 可否替換 | ✅ writable + configurable，prototype 未凍結，instance 無自有 emit |
| 一次 patch 能否涵蓋所有連線        | ✅ 遊戲同開 6 條，全部共用同一 prototype                           |
| 能否不 patch 就監聽全部進來的事件  | ✅ `WSClient.onAny`                                                |
| OK 鈕物件                          | ✅ `MainA` 場景，材質 `ok`，(570, 630)                             |
| 遊戲怎麼做「不可按」               | 切 frame `"2"` + `input.enabled = false`                           |
| 對手動作                           | ✅ `cardclickedB` / `cardrotateB`                                  |
| 對手按下 OK 我方收不收得到         | ❌ **收不到**，見下方「對手的 OK 狀態不會外洩」                    |

### 設計輪廓

1. 攔 `emit("I_am_ok", …)`，不往下送，改記本地「假鎖定」狀態
2. 切 OK 鈕的 frame 做假鎖定的視覺
3. 收到 `cardclickedB` / `cardrotateB` → 自動解除我方假鎖定
4. 雙方插件確認都已假鎖定 → 各自用**原始 emit 重放攔到的那次呼叫**

第 4 點很關鍵：**原封不動重放攔截到的參數**，插件就完全不需要知道
`I_am_ok` 的協定長什麼樣，遊戲改版改了參數也不會送錯東西。

### 倒數計時：已知與未知

**伺服器不告訴客戶端秒數。** `timerReset` / `timerstop` / `timerPause` /
`timerResume` 的 `args` 全部是空陣列 `[]`，倒數長度寫死在遊戲 JS 裡。

> 附帶結論：討論中提過的「把移動階段秒數設為 25 秒」只會改本機顯示，
> 不會改變伺服器的實際判定。

**機會三卡、聖水卡會凍結倒數**，凍結期間雙方都不能操作。對應到
`timerPause` / `timerResume`，插件偵測得到。任何安全邊際的計算
**必須扣掉凍結時間**。實測序列：

```
→送出 card            我方出牌
      _cardclickedA
←收到 timerPause       立刻凍結
←收到 okInvisibleA     OK 鈕變不可按
```

全部 log 只有 5 次 `timerPause`，遠少於出牌次數 —— 確實只對特定卡觸發。

### Q1 已解答：伺服器自己結束回合 ✅

2026-07-28 實測，讓倒數自然歸零、我方完全沒送 `I_am_ok`，回合照樣結束了。

- 攔截 `I_am_ok` **不會**變成「永遠不逾時」的作弊 ✅
- 但插件壓著不送，時間到就等於棄權。**必須在歸零前自己補送。**

### ⚠ 倒數要量 `okVisibleA` → `okInvisibleA`，不是 `timerReset` → `timerstop`

第一版量錯了。`timerReset` → `timerstop` 量到 80.03s / 83.4s，但玩家都知道
移動回合是 **30 秒** —— 因為那個區間是**整個階段**，包含好幾個回合加上動畫
與非互動空檔。實測有一次 `okVisibleA` 在 `timerReset` 之後 **48 秒**才出現，
那 48 秒根本不能按 OK。

真正的倒數是 OK 鈕可用的那段：

```
20:58:52  okVisibleA
20:59:23  okInvisibleA    ← 31s
20:59:36  okVisibleA
21:00:07  okInvisibleA    ← 31s
21:00:57  okVisibleA
21:01:28  okInvisibleA    ← 31s
```

三次都 31.0 秒 = 遊戲顯示的 30 秒 + 約 1 秒伺服器回報延遲。

**安全邊際一律從 `okVisibleA` 起算。** 不同階段（抽牌／移動／攻擊／防禦）
的秒數可能不同，樣本還在累積 —— 每種階段 3 個以上、且區間小於 1.5 秒即可。

### 對手的 OK 狀態不會外洩 ✅

這件事決定了功能在「對手沒裝插件」時能做到什麼，也決定它符不符合 §12。

實測所有 battle log 的真實事件欄位（不是 `meta.ACKs` 裡的字串參照）：

| 事件           | 次數 | 方向                        |
| -------------- | ---- | --------------------------- |
| `okVisibleA`   | 98   | ←收到（**我方** OK 鈕可用） |
| `I_am_ok`      | 90   | **→送出。一次都沒有收到。** |
| `okInvisibleA` | 9    | ←收到                       |
| `okVisibleB`   | 3    | ←收到                       |
| `okInvisibleB` | 1    | ←收到                       |

B 側那 4 次的前後文顯示它們**不是**「對手按了 OK」：

```
drawPhase → eventCard → endDrawPhase → cardController1B → okVisibleB → phaselabel_A
                                                          ↑ 階段開始，啟用對手 OK 鈕

→送出 card → _cardclickedB → timerPause → okInvisibleB → cardController2B
                              ↑ 凍結      ↑ 凍結時雙方 OK 鈕都停用

goToBochi → okVisibleB → timerResume
            ↑ 解凍，兩邊恢復
```

也就是它們反映**階段與凍結狀態**，與對手是否按下 OK 無關。

> **伺服器從不告訴客戶端對手按了 OK。** 所以「對手沒開插件時，我方也看不到
> 對方是否按了 OK」這個 fairplay 要求是**協定本身保證的**，不是靠我們自律
> —— 這比約定不使用強得多。

> ⚠ 分析陷阱：直接 grep `I_am_ok` 會匹配到封包 `meta.ACKs` 裡的字串參照，
> 看起來像是「收到」了 378 次。一定要解析 JSON 只看 `event` 欄位。
> 另外舊 log 有 3 欄（無 port）與 4 欄兩種格式，只處理 4 欄會靜默丟掉
> 1690 行 —— `okVisibleB` 全都在那些行裡。

### 建議的分期

先前草擬的單邊方案有一步是「收到對手已鎖定的訊號 → 立刻送出真 OK」。
上一節已證明**那做不到** —— 伺服器不下發對手的 OK 狀態。這推翻了
「單邊就能完整解決」的說法，因為：

> 按 OK 之所以能提早結束階段，是因為雙方都按了。如果插件把 OK 壓到
> 安全邊際才送，**每個階段都會跑滿 ~80 秒**，自己反而變成拖條仔。

所以分期改成：

**第一期（單邊，小而安全）：3 秒誤按反悔窗口。** ← 已拍板

定位是**解決誤按**，不是反拖條。這個講法沒有爭議，也誠實。

1. 攔 `I_am_ok`，記成本地「假鎖定」，切 OK 鈕 frame 做視覺
2. 對手動作（`cardclickedB` / `cardrotateB`）→ 解除假鎖定，可以重選
3. 假鎖定滿 3 秒且對手無動作 → 送出真 OK
4. 視窗剩餘時間不足 → **縮短窗口並立刻送出**，絕不讓玩家逾時棄權

30 秒的視窗配 3 秒窗口綽綽有餘，只有在「剩不到 5 秒才按 OK」時第 4 點才會
生效。量測工具的統計會列出這種情況佔多少比例。

代價是每回合多 3 秒。不需要對手裝插件。

**第二期（雙邊，真正的解法）：** 兩邊都假鎖定 → 同時送真 OK。
因為遊戲不告訴你對方狀態，這需要一條側通道交換「我準備好了」。
這才是燈皇原本描述的東西。

公平性是自動的：**對手沒插件 = 沒有側通道 = 我們什麼都不知道**，
只能退回第一期的行為。不需要額外的偵測或自律機制。

> **雙開讓第二期提前可做。** 原本第二期卡在「要先有 ULGG 側通道」，
> 但兩個客戶端跑在同一台機器時（UL 視窗版 :9333 + Chrome 網頁版 :1221），
> 插件可以直接用 localhost 串起來，把整套握手協定驗完，之後再把傳輸層
> 換成 ULGG 或 P2P。協定本身不用重寫。
>
> 同時也是安全的測試場：攔截 `I_am_ok` 這種會影響勝負的東西，自己對自己
> 打不會害到別人。工具：`Desktop\Unlight\雙開對照.py`

**第三期**的「快結束時動牌給對方額外 5 秒」暫不做 —— 5i 已指出可以
故意在剩 5.01 秒時全收回挖坑，規則本身還沒收斂。

### 社群立場要注意

拖條在社群裡**有爭議**，不是共識性的濫用行為。有玩家明講會刻意慢按 OK
當作對「跟牌」的反制。所以功能定位不是「禁止慢慢想」，而是**消除
「先按 OK 的人被懲罰」這個不對稱** —— 兩邊都保有思考時間，只是不能再從
對方的提早承諾裡拿到資訊優勢。文案要照這個講，不要寫成抓拖條仔。

## 5. 已經做的決定（不用再討論）

| 決定                                   | 理由                                                                                     | 出處              |
| -------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------- |
| 正規化用 RFC 8785 (JCS)                | §5.2 要求的四件事就是它的定義；各語言有現成實作可對照                                    | 本 repo           |
| COST 精度 0.01，最多兩位小數           | 0.5 的粒度太粗無法平衡。0.01 不影響 Hash（JCS round-trip 是確定性的），只影響加總        | `cost-number.ts`  |
| 引擎內部一律用整數百分之一運算         | `8.8+26.6+26.6 = 62.00000000000001`，剛好卡滿上限的隊伍會被誤判超標                      | `toCentiCost`     |
| 精度檢查不寫進 JSON Schema             | `multipleOf: 0.01` 是 `value/0.01` 判整除，`4.35/0.01 = 434.99999999999994` 會誤判合法值 | `validate.ts`     |
| `restrictions` 只支援 `agreement-only` | §12 禁止把遠端資料轉譯成可執行邏輯，條件字串永遠不解析                                   | `types.ts`        |
| 壓 C 用區間表不用條件式                | 第一版不做條件引擎，否則 Client 與網站對接複雜度暴增                                     | `CompressionRule` |
| contentHash 不放在規則內容裡           | 會變成雞生蛋。Hash 住在外層的 `.ulrcost.json` 信封                                       | `rule-package.ts` |
| 壓 C 區間不得重疊                      | 重疊會讓同一差距對應兩個追加值，違反 §9「確定性結果」                                    | `validate.ts`     |
